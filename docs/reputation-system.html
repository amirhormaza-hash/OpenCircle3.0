1 System Overview

OpenCircle uses three interlocking systems to measure and reward user quality:

  • Behavior Score — a running integer that reflects how reliably and respectfully a user participates. Every action in the app can add or subtract points.
  • User Reputation Score — a 0–5 star rating calculated from peer reviews left by other attendees after events. Separate from the behavior score.
  • Badges — permanent achievement medals awarded once when a user crosses a specific milestone. Earning a badge also adds a one-time bonus to the behavior score.
ℹ️
All score mutations happen server-side through Supabase Edge Functions (add-points, deduct-points, check-achievements). The client can never directly modify its own score, ensuring integrity.

2 Behavior Score

Starting Value

Every new account begins with a behavior score of 1,000 points. This places new users immediately in the Reliable tier, giving them full access to join and host events from day one.

How it works

The score is a non-negative integer stored in profiles.behavior_score. It can never go below 0. Every transaction — positive or negative — is immutably logged in behavior_score_log with the action name, point delta, and running total, creating a full audit trail.

Trust Tier

After every score change the server recomputes the user's Trust Tier and updates profiles.trust_tier and profiles.is_restricted automatically. The tier determines what actions the user can take in the app.

6 New-User Protection

New users are given a grace period during which minor mistakes don't immediately harm their score. This encourages genuine participation without fear of being permanently disadvantaged by an early mistake.

How Protection Works

  • Protection is active for 30 days from account creation, stored in new_user_protection_expiry.
  • Protection automatically expires early if the user's score exceeds 1,050 — indicating they're no longer a genuine newcomer.
  • During the protection window, the first no-show is converted to a warning (no points lost). The same applies to the first late cancellation.
  • After each first-offence warning, the corresponding flag (first_no_show_warning_given, first_late_cancel_warning_given) is set to true — the next offence will deduct points normally, even within the protection window.
✅
What protection covers: first no-show, first late cancellation.
What it never covers: inappropriate-behaviour violations (harassment, hate speech, fake reviews, predatory behaviour, inappropriate content).

8 Event Rating Formula

Each completed event gets an aggregate star rating displayed publicly on event cards. The formula is designed to be generous but not inflatable — silent attendees (those who didn't leave a review) contribute positively but at half weight.

The Formula

R = (sum_actual + silent_count × 2.5) / (5 × (reviewer_count + silent_count / 2)) score = R × 5 → range [0.0, 5.0]

Variable Definitions

VariableMeaning
sum_actualSum of all explicit star ratings (1–5) submitted by reviewers
reviewer_countNumber of attendees who submitted an explicit star rating
silent_counttotal_attendees − reviewer_count — those who attended but didn't review
silent_count × 2.5Each silent attendee contributes the equivalent of a half-weight 5★ review

Worked Example

An event has 10 total attendees. 4 leave reviews: two 5★, one 4★, one 3★. The other 6 attended silently.

sum_actual = (5+5+4+3) = 17 silent_count = 10 − 4 = 6 reviewer_count = 4 numerator = 17 + (6 × 2.5) = 17 + 15 = 32 denominator = 5 × (4 + 6/2) = 5 × 7 = 35 R = 32 / 35 ≈ 0.914 score = 0.914 × 5 ≈ 4.57 ★

When is a rating shown?

  • If total_attendees = 0 → rating is null (not displayed)
  • If reviewer_count = 0 → "No reviews yet"
  • Otherwise → the computed score is shown rounded to 2 decimal places

Review Window

⏱️
Event star ratings can only be submitted within a 48-hour window after the event ends. This deadline is enforced server-side by Supabase RLS policy on the event_ratings table — the client cannot bypass it. After the window closes the row becomes read-only.

9 User Reputation Score

The user reputation score measures how well-regarded a person is by their peers, based on star ratings received after events. It is distinct from the behavior score.

Two Calculation Modes

ModeConditionFormula
New Fewer than 3 ratings received Displays as "New" — too few data points
Bootstrap 3 – 10 ratings received Simple average of all ratings
Full More than 10 ratings received 60 % weight on last 10 ratings + 40 % weight on all older ratings

Full Mode Formula

recent_avg = average of the last 10 ratings received old_avg = average of all ratings before the most recent 10 score = (0.4 × old_avg) + (0.6 × recent_avg) → range [0.0, 5.0]
💡
The 60/40 split means recent behaviour matters more than historical. A user who previously had a low reputation can actively improve it by earning better ratings in recent events. Ratings are ordered oldest → newest for the calculation.

User Rating Submission Flow

User-to-user ratings are submitted from another user's profile page. The following rules are enforced:

  • Shared attendance required: you can only rate someone you attended an event with. The app finds the most recent shared event where you haven't already rated them.
  • One rating per (rater, rated, event) triplet: enforced by a UNIQUE(rater_id, rated_id, event_id) constraint in the user_ratings table. Rating the same person again for a different shared event is allowed.
  • Star score + tags submitted together: the rater provides a 1–5 star score and selects one or more reputation tags in the same submission. Both are stored on the same user_ratings row.
  • Score precision: the score column is NUMERIC(2,1), allowing half-star granularity (e.g. 4.5) in future if the UI supports it. Currently the UI collects whole stars only.
  • Points awarded on submit: the rater earns +5 (leave_review) and the rated user earns +10 for a 5★ or +5 for a 4★ via the add-points edge function.
🔍
After a rating is submitted, check-achievements is called for both the rater and the rated user so that any newly triggered badges (e.g. First Timer, Social Butterfly) are awarded immediately.

10 Reputation Tags

Reputation tags are short qualitative labels that attendees can attach to a user-to-user rating. They give a human-readable summary of someone's social presence beyond a star number, and are displayed as counts on every user's profile page.

The 10 Available Tags

Tags are defined as a fixed constant list in the app (src/constants/reputationTags.ts). A rater may select any combination of them when submitting a rating.

😊 Friendly ✅ Reliable 🎉 Fun 👑 Great Host 📋 Organized 🤝 Welcoming ⚡ Active ✨ Good Vibes 🙏 Respectful ⏰ Punctual

How Tags Are Stored

Tags are stored as a TEXT[] array on the user_ratings row alongside the star score. Each tag received is counted client-side from the raw array via fetchReputationTags(userId), which returns a map of { tagName: count }.

Vouch Count

The profile page shows a single vouch count number — the total of all tag instances a user has ever received across all their ratings. This is computed by fetchVoucheCount(), which simply sums the values from the tag count map. A user who received "Friendly × 8, Reliable × 5, Fun × 3" has a vouch count of 16.

📌
Tags do not directly affect the behavior score or reputation score — they are a display-only social signal. The only score impact comes from the star component of the same rating (see §9).

12 Badge Unlock Logic (Technical)

Badges are evaluated by the check-achievements Supabase Edge Function. It is called server-side after each relevant event (attendance, score change, message sent). The function never re-awards a badge the user already holds.

Evaluation Flow

  1. Fetch the user's existing badges into a Set (alreadyEarned).
  2. In parallel, query: total attended count, category breakdown, early-join records, streak, hosted event ratings, social messages, Diamond threshold date, current behavior score.
  3. Evaluate each badge condition. If the condition is met and the badge is not already earned → add it to toAward.
  4. Upsert all newly earned badges with seen = false (triggers the in-app notification dot).
  5. For each new badge, add the bonus points to the behavior score sequentially (to keep the running total accurate) and write a log entry with action = badge_{key}.

Diamond Badge — Special Tracking

The Diamond badge requires the score to stay at 1,200+ for 30 consecutive days. This is tracked via the achievement_progress table:

  • When the score crosses 1,200 upward for the first time, diamond_threshold_reached is set to the current timestamp.
  • If the score drops below 1,200 at any point, diamond_threshold_reached is reset to null — the 30-day clock restarts.
  • The badge is only awarded when score ≥ 1,200 AND now() − diamond_threshold_reached ≥ 30 days.

Social Butterfly — How Chats Are Counted

The function infers distinct event chats from behavior_score_log rows where action = 'event_chat_message'. The context JSON field on each log entry stores the event_id. Distinct event_id values are counted — the badge requires at least 10 unique event chat rooms with at least one message sent.

Early Bird — Timing Calculation

For each event the user joined, the function compares event_attendees.created_at (when they joined) against event.date_time (event start). If the gap is ≥ 24 hours (86,400,000 ms), it counts as an early join. The badge requires at least 5 such events.

Host Badge — Rating Verification

The function fetches all events where profile_id = user_id, then pulls all event_ratings for those events. It groups stars by event and computes a simple average. If any hosted event has an average > 3.0★, the badge is awarded.

13 Streaks

Weekly attendance streaks are tracked separately in the user_streaks table and are managed by the update-streak Edge Function, called after each confirmed attendance.

Streak Rules

  • A "week" is a rolling 7-day window — attending at least one event per 7 days keeps the streak alive.
  • Missing a full 7-day window resets current_streak to 0. longest_streak is never reset.
  • current_streak is the number of consecutive weeks with at least one attended event.
  • longest_streak is the all-time personal best consecutive-week count, updated whenever current_streak exceeds it.
  • last_attended_week stores the ISO date of the Monday that started the most recently active week, used to detect gaps.
  • The On Fire badge requires current_streak ≥ 3.

Streak Columns (user_streaks)

ColumnTypeMeaning

longest_streakINTAll-time personal best. Never decreases.
last_attended_weekDATEMonday of the last week the user attended an event.
